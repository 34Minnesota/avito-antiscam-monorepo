# Архитектура MVP «Антискам тренажёр»

## Summary

- Модульный монолит: Go API + React SPA + PostgreSQL в одном Docker Compose. Это покрывает обязательные требования кейса: Go, выбираемая БД, Compose, линтеры, тесты и общий репозиторий. [Требования кейса](C:\Users\User\VSCode\avito-antiscam\docs\case.md)
- PostgreSQL — основная БД. Граф сценария хранится реляционно: `scenario_versions → scenario_nodes → scenario_transitions`; графовую БД вводить бессмысленно для 4 сценариев.
- Все четыре сценария открыты с начала. «Уровень» = отдельный сценарий; прогресс показывает прохождения и лучший результат, а не блокирует жюри контентом.
- ИИ — отдельный режим поздней очереди, не зависимость основного demo path.

## Данные и движок

- Каноническая схема — SQL-миграции в `backend/migrations`; `docs/schema.yaml` — читаемая YAML-документация таблиц, связей, ограничений и ER-диаграммы. Не нужно делать YAML вторым источником DDL: это гарантированный рассинхрон.
- Сущности:
  - `anonymous_sessions`: UUID сессии, даты создания/последней активности; никаких персональных данных.
  - `scenarios`: стабильный `slug`, роль (`buyer`/`seller`), модуль риска, название и публичность.
  - `scenario_versions`: неизменяемая опубликованная версия сценария и стартовый узел.
  - `scenario_nodes`: узлы направленного графа (`scene`, `decision`, `ending`), отображаемый контент и порядок.
  - `scenario_transitions`: разрешённые переходы, выбранный вариант, целевой узел, изменение score и объяснение последствия.
  - `risk_markers`, `transition_risk_markers`: нормализованные признаки риска для итогового разбора.
  - `attempts`: попытка, зафиксированная версия сценария, текущий узел, score, status, revision.
  - `attempt_steps`: неизменяемый журнал выбранных переходов.
- Инварианты SQL: уникальность ключа узла в версии; переходы возможны только между узлами одной версии; один стартовый узел на версию; одна попытка ссылается на конкретную опубликованную версию; повторный POST действия не создаёт второй шаг.
- Движок выполняет действие транзакционно: проверяет владение попыткой через `X-Session-ID`, её `revision`, текущий узел и допустимый переход; сохраняет `attempt_step`, обновляет попытку и возвращает immediate feedback + следующий экран. На терминальном узле вычисляет итог по `attempt_steps` и связанным `risk_markers`.
- Seed-данные: 4 открытых сценария — у покупателя «фишинговая доставка» и «увод в сторонний мессенджер»; у продавца «ложная предоплата/фальшивое подтверждение» и «выманивание SMS-кода». Каждый содержит несколько веток, безопасный и рискованный финалы.

## API и репозиторий

- `docs/openapi.yaml` — источник контракта OpenAPI 3.1; `oapi-codegen` генерирует Go-типы и интерфейс сервера. В спецификации у каждого DTO обязательные JSON Schema, примеры и коды `400`, `401`, `404`, `409`, `422`, `500`.
- Минимальные операции:
  - `POST /v1/sessions` — создать анонимную сессию, вернуть `sessionId`.
  - `GET /v1/scenarios` — доступные уровни и лучший результат.
  - `POST /v1/scenarios/{slug}/attempts` — начать новую попытку.
  - `GET /v1/attempts/{attemptId}` — восстановить экран незавершённой попытки.
  - `POST /v1/attempts/{attemptId}/actions` — выбрать действие с `expectedRevision`; вернуть объяснение, следующий узел либо итог.
  - `GET /v1/progress` — агрегированный прогресс по ролям и сценариям.
  - `GET /healthz` — healthcheck Compose.
- `X-Session-ID` обязателен во всех операциях, кроме создания сессии. Это сознательно слабее HttpOnly-cookie, но соответствует выбранному MVP и упрощает интеграцию SPA.
- Структура:

```text

│   ├── cmd/api/
```

- Стек: Gin, pgx, golang-migrate, oapi-codegen; React + TypeScript + Vite. ORM не используется.
- Compose: PostgreSQL с volume и healthcheck; migration job; API после успешных миграций; frontend собирается в Nginx и проксирует `/api` в backend. Наружу публикуется только frontend.

## Проверка

- Unit-тесты движка: допустимый/недопустимый переход, terminal state, расчёт score, повтор POST, устаревший `revision`, доступ к чужой попытке.
- Интеграционные тесты PostgreSQL: миграции, ограничения версии графа, полный путь каждого из 4 seed-сценариев.
- Contract-тесты: API-ответы соответствуют `docs/openapi.yaml`; frontend генерирует клиент из этой же спецификации.
- Проверка Compose: чистый `docker compose up --build` поднимает БД, миграции, API и SPA; пользователь проходит каждый сценарий от старта до итоговой обратной связи.

## Assumptions

- Админский редактор сценариев, регистрация, JWT и AI-диалог не входят в MVP: сценарии поставляются миграциями/seed-данными.
- ИИ добавляется только после стабильного основного пути, за feature flag и с шаблонной fallback-обратной связью при ошибке провайдера.
- Требование кейса — обучающий продукт с последствиями выбора, обратной связью, ролями и видимым прогрессом; предложенная модель напрямую это реализует. [Требования кейса](C:\Users\User\VSCode\avito-antiscam\docs\case.md)
